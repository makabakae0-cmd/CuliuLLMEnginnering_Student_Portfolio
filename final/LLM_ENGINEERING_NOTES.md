# Fungi Simulator 大模型工程说明

本文档说明 Fungi Simulator 中与大模型相关的工程设计。重点不是罗列概念，而是解释项目实际用了什么、为什么这样设计、解决了什么问题，以及如何验证它有效。

产品介绍见 `README.md`；本地部署和接口运行见 `TECHNICAL.md`；测试与失败复盘见 `TEST_AND_FAILURE_LOG.md`。

## 1. Prompt

项目中使用 Prompt 的位置主要有三类：真菌孢子策略、宿主行动决策、感染阶段解说。

### 真菌孢子策略

- 使用内容：真菌类型、环境、地图层级、可部署位置、孢子数量和游戏目标。
- 设计原因：真菌方需要根据地图和规则部署孢子，但不应该知道宿主出生点，否则游戏会失去公平性。
- 输出要求：尽量生成结构化部署结果，方便前端解析和确认孢子位置。
- 验证方式：检查生成结果是否在合法格子内，数量是否符合规则，失败时是否能进入本地部署 fallback。

### 宿主行动决策

- 使用内容：宿主类型、当前位置、巢穴目标、剩余步数、可行动作和当前层级。
- 设计原因：宿主 AI 的目标是模拟“有限信息下的求生行为”，而不是读取隐藏孢子后作弊。
- 输出要求：给出下一步动作或短路线计划。
- 验证方式：检查宿主 AI 不读取隐藏孢子位置、最近孢子距离或陷阱提示；AI 失败时走本地启发式行动。

### 感染阶段解说

- 使用内容：感染阶段、宿主状态、真菌类型、当前事件和模拟进度。
- 设计原因：感染过程比较抽象，需要把阶段变化转成适合课堂理解的中文解释。
- 输出要求：用科普语言解释“发生了什么”和“为什么会这样”，避免血腥、恐怖或误导表达。
- 验证方式：检查每个阶段都有可读解说；GLM-5 不可用时使用 `buildLocalAICommentary()`。

## 2. RAG

RAG 用于知识问答和感染阶段解释，目标是减少模型只凭记忆回答导致的幻觉。

- 使用内容：真菌、宿主、感染阶段、死亡紧咬等生物相关资料。
- 设计原因：课堂问题可能超出当前游戏状态，需要从知识库检索证据后再回答。
- 入口接口：`/api/rag/health` 检查知识库状态，`/api/rag/ask` 处理问答。
- Fallback 边界：当 ChromaDB 不可用时，可以使用本地关键词检索，但默认来源必须限制为生物材料。
- 已修复问题：曾经把 `Agent_completion_workbook.md` 等工程文档纳入 fallback，导致生物问题检索到版本表或工程说明；现在已移除技术文档来源，并加入 death grip / 死亡紧咬内置生物片段。
- 验证方式：检查 RAG 回答是否展示检索片段、source titles 或 source ids；检查 `/api/rag/health` 是否能返回 collection、count、embedding 或具体错误。

## 3. Tool Calling

项目没有复杂的外部工具链，但把后端 API 作为可控工具入口使用。

| Tool / API | 作用 | 为什么这样设计 |
|---|---|---|
| `/api/generate` | 统一代理 GLM-5 生成策略或解说 | 前端不直接暴露 API Key，失败时可集中处理 |
| `/api/rag/ask` | 基于知识库回答课堂问题 | 把知识问答和普通生成分开，便于展示证据 |
| `/api/health` | 检查后端是否可用 | 演示前快速确认服务状态 |
| `/api/rag/health` | 检查 RAG 依赖和知识库状态 | RAG 重依赖失败时不阻塞主服务 |

验证方式包括：健康检查返回可读状态、生成接口失败时前端不中断、RAG 不可用时页面能展示可读错误。

## 4. Memory

项目不保存长期个人记忆，也不记录用户隐私数据。这里的 Memory 指项目运行中的临时状态和维护状态。

- 运行状态：当前地图、宿主位置、感染阶段、回合进度、自动演示状态。
- 教学状态：当前解说文本、RAG 问答结果、检索片段。
- 维护状态：`.cursor/skills/` 中的 pipeline、minimal state、inputs、outputs、validations、fallbacks。

设计边界：

- 不把真实 `ZHIPUAI_API_KEY` 写入文档、前端或日志。
- 不把隐藏孢子位置提供给普通宿主 AI。
- 不把宿主出生点提供给真菌 AI。
- 不保存完整用户聊天或课堂提问作为长期记忆。

## 5. Agent

项目中的 Agent 更接近“功能型智能模块”，每个模块负责一个明确任务。

- 真菌 AI：根据地图和规则规划孢子部署。
- 宿主 AI：在有限信息下规划移动路线。
- 感染后宿主 AI：感染后尝试找食物、换层或等待保命。
- AI 解说：根据当前阶段生成科学解释。
- RAG QA：回答课堂追问并展示证据。
- 自动演示控制器：串联配置、部署、移动、感染和结算流程。

设计判断：每个 Agent 的输入范围要小，避免把整个游戏状态无差别塞给模型。这样可以减少作弊信息泄露，也便于失败时切换到本地 fallback。

## 6. Multi-Agent

AI vs AI 自动演示是项目中的 Multi-Agent 场景。它不是多个模型同时对话，而是多个智能模块按游戏状态顺序协作。

流程如下：

```text
配置真菌/宿主/环境
→ 真菌 AI 部署孢子
→ 宿主 AI 规划移动
→ 系统判断是否触发感染或到达巢穴
→ 感染后宿主 AI 尝试求生
→ AI 解说解释当前阶段
→ 系统生成胜负结算
```

关键修复：

- 自动演示必须产生可解释结局，不能停在“未触发胜负页面”。
- 快进倍率不只影响感染计时，也要影响宿主移动、感染后求生、食物刷新等等待时间。
- 回巢和感染后求生尽量先规划路线，再逐步播放，避免“走一步想一步”导致演示过慢。

## 7. Safety Guard

项目的安全边界主要围绕 API、游戏公平性和科普表达。

- API 安全：真实 API Key 只通过环境变量提供，不写入 README、截图或前端代码。
- 信息隔离：宿主 AI 不读取隐藏孢子；真菌 AI 不读取宿主出生点。
- 表达安全：感染解说聚焦科学机制，不渲染血腥、恐怖或误导内容。
- RAG 安全：知识问答默认只检索生物相关资料，避免把工程文档当作科学资料。
- 演示安全：外部服务失败时页面给出可解释状态，而不是空白或卡死。

## 8. Fallback

Fallback 是为了保证课堂演示不断线。

| 失败点 | 兜底方案 | 目的 |
|---|---|---|
| GLM-5 API 失败 | 使用本地孢子部署、宿主行动或 `buildLocalAICommentary()` | 外部网络不通时仍能演示 |
| RAG 不可用 | 显示可读错误或使用受限本地生物材料 | 避免问答区完全不可用 |
| 自动演示超时 | `forceAutoDemoResult()` 强制结算 | 保证有明确结局 |
| 感染后宿主 AI 失败 | 本地找食物、换层、等待策略 | 保证感染后行为继续 |
| ChromaDB 只读或依赖缺失 | `/api/rag/health` 返回诊断 | 方便定位环境问题 |

Fallback 不等于最终答案。它的目标是维持演示完整性，科学准确性仍应优先依赖经过校对的知识库和人工复核。

## 9. Trace

一次自动演示的关键状态流如下：

```text
startAutoDemo
→ prepareAutoDemoGame
→ generateAISpores
→ host route planning
→ moveHost
→ infection check
→ enterInfectionMode
→ runInfectedHostAIDemoLoop
→ AI commentary or local commentary
→ RAG fact or local stage guide
→ forceAutoDemoResult if needed
→ victory / failure screen
```

Trace 的作用是帮助排查“卡在哪一步”：如果没有生成孢子，就看 `/api/generate` 或孢子 fallback；如果感染后没反应，就看 infected host loop；如果没有胜负页面，就看强制结算；如果知识问答跑偏，就看 RAG source。

## 10. 测试与失败分析

完整记录见 `TEST_AND_FAILURE_LOG.md`。

当前测试覆盖：

- 首页与产品介绍。
- 游戏配置与开始流程。
- AI vs AI 自动演示。
- 感染阶段模拟与 AI 解说。
- RAG 知识问答。
- 后端健康检查。

典型失败案例：

- GLM-5 API 返回 `502 upstream_network_error`：使用本地 AI 解说 fallback，演示不中断。
- 自动演示结束出现“未触发胜负页面”：新增强制结算，保证可解释结局。
- RAG 问答检索到错误材料：移除工程文档作为默认 fallback 来源，只保留生物相关资料。

这些测试和失败记录用于证明：项目不是只把大模型接进页面，而是考虑了网络失败、检索污染、信息隔离、演示结算和课堂可用性。
